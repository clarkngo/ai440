HOS 3: Simulation, Synthetic Data & Sim-to-Real

Build a simulated packaging cell in MuJoCo, export it to OpenUSD, render labeled synthetic images, train a pushing policy with and without randomized physics on CPU, then measure on held-out worlds how each one holds up when the world changes.

🧭

Before you start

  1. Know the concepts. Read Concept Companion → Module 3 and try its self-check before you open the starter code.
  2. Rehearse it. The Sim-to-Real Lab plays the finished build in your browser; its guided tour takes about 15 minutes.

What you'll need

  • Starter code: your own HOS 3 repo, opened in GitHub Codespaces. Planned The HOS 3 starter repository and its GitHub Classroom invite are being built and tested; the invite link goes here when they are published. Not sure what a file does? See the starter code walkthrough for this HOS.
  • A GitHub account. No GPU and no paid service: MuJoCo, usd-core, BlenderProc, Gymnasium and Stable-Baselines3 are free and open source.
  • The default 2-core Codespace and some patience: training takes about 10 minutes, the first BlenderProc run downloads Blender (about 400 MB), and each image takes a second or two to render.

Reference reading (optional, before you start)

  • MuJoCo Python bindings: loading a model, stepping it, and changing model arrays at run time.
  • Introduction to OpenUSD: prims, stages and layers, enough to read your .usda file.
  • Stable-Baselines3: PPO: the algorithm and its settings, and why it runs fine on CPU for small policies.

This HOS is graded across four stages instead of on code correctness alone: Engagement (Create/Scaffold) is 20% of the HOS grade, and Skills is 80%: Evaluate, Analyze, Apply (the change you make by hand in Understand & Refine) and Understand (your own explanation of it), 20% each. Each stage below says exactly what to submit. Everything goes in your Module 3 GitHub Classroom repo: written work under the matching heading in NOTES.md, screenshots in screenshots/. Commit and push as you go. By the end of Week 6, push your final work: your repo is your submission, so there is nothing to submit in Brightspace, and your last push before the deadline is what counts.

1 · Create / Scaffold

Week 5 · Wed–Thu

Graded as Engagement: 20% of this HOS. The AI-built starting point, not the deliverable.

Get the simulated cell running, its scene description exported, a set of labeled images rendered, and, with an AI coding assistant, two pushing policies trained: one fixed, one randomized. The cell, the exporter and the renderer are in the starter. This is the starting point, not the deliverable; whether it transfers is what Evaluate is for.

  1. Open your own HOS 3 repo in GitHub Codespaces (its .devcontainer installs MuJoCo, Gymnasium, CPU-only Stable-Baselines3, usd-core and BlenderProc). Planned The HOS 3 starter repository and its GitHub Classroom invite are being built and tested; the invite link goes here when they are published.
  2. Run the cell once: python -m simulation.run_once writes renders/first_frame.png. Then export it: python -m simulation.export_usd writes scene/cell.usda. Open the file and find the carton.
  3. Give your assistant the prompt below, then start python train.py. It takes about 10 minutes on two cores; carry on with the next step while it runs.
  4. Render the labeled images: blenderproc run synth/render_parts.py --n 200. The first run downloads Blender (a few minutes); after that, each 256 × 256 image takes a second or two on CPU.

The prompt

Use an AI coding assistant in Agent mode (GitHub Copilot is free for students in Codespaces). Give it this prompt as written, and read what it changed before you run anything:

In THIS existing workspace (the starter-code folder that's already open),
edit files here; do not create a new workspace or project.
In simulation/randomize.py, write randomize(model, rng, cfg) for a
loaded mujoco.MjModel:
- At the start of each episode, set the carton's sliding friction
  (model.geom_friction for the geom "carton_geom") and its mass
  (model.body_mass for the body "carton") to the base values times
  factors drawn uniformly from cfg.FRICTION_RANGE and cfg.MASS_RANGE
  (both in simulation/config.py). Change the arrays directly; do not
  reload the XML.
- Return a dict of the values used, so they can be logged.
In simulation/push_env.py, call randomize() in PushEnv.reset() only
when PushEnv(randomize=True).
In train.py, train two Stable-Baselines3 PPO policies with
device="cpu": randomize=False and randomize=True, 150_000 steps each,
seed=0, saved to policies/fixed.zip and policies/randomized.zip, with
plots/training.png showing both learning curves.
It must finish in under 10 minutes on a 2-core Codespace.
Make pytest pass.

Gotchas to expect: (1) The assistant may build in a new workspace instead of your starter folder; use Agent mode and say "this existing workspace". (2) There is no GPU: if it sets device="cuda" or installs a CUDA build of PyTorch, training fails or the disk fills up. Keep device="cpu" and the pinned requirements.txt. (3) Headless rendering needs MUJOCO_GL=osmesa, which the .devcontainer sets; if the assistant changes it, run_once fails with an OpenGL error. (4) If the assistant reloads the XML every episode, training gets ten times slower.

Submit (Engagement)

  • Paste the prompt you gave your AI assistant under Create in NOTES.md, add plots/training.png and renders/samples.png (a grid of nine of your images) to screenshots/, then commit and push to your Module 3 repo.

2 · Evaluate

Week 5 · Fri–Sun

The critical gate — is the AI-built result actually right?

Did the policies learn to push, or to push in one simulator? Do the images and labels match? evaluate.py runs each policy 50 episodes on each of six held-out worlds: altered friction and mass, some inside the training ranges and some outside. Run each of these and write down what happened:

  • The gap: run python evaluate.py --worlds heldout. For each world, which policy wins and by how much? How much does the randomized one give up on its home world?
  • Too wide: retrain the randomized policy with --range wide (friction 0.1–3.0) and evaluate it. Did it learn at all? What does its training curve show?
  • Labels: run python synth/check_labels.py, which draws the labels over twelve random images. Is any box wrong, cut off, or on a part hidden behind the arm?
  • Cost: how long did training and rendering take? From your render time, how many images fit in an hour on two cores, and what would doubling the resolution cost?

Submit

  • Paste this note under Evaluate in NOTES.md, add the tables and label checks to screenshots/, then commit and push by the end of Week 5. Your commit history is your Week 5 checkpoint.

3 · Analyze

Week 6 · Mon–Tue

Why does this work, mechanically?

Pick one of these and explain it in your own words. Depth beats breadth: one mechanism explained well scores higher than a tour of every file. Your instructor may ask a follow-up about one line, so write it so you could answer.

The sim-to-real gap

Which altered world hurt most, and what the policy relied on.

  • Which held-out world hurt the fixed policy most? Explain, from what the policy saw in training, why that world in particular.
  • Trace randomize() from PushEnv.reset() to the arrays it changes. Quote the lines.
  • Name one thing a real cell varies that none of your held-out worlds do.

The randomization ranges

How randomize() draws each value, and what too wide does.

  • Where did FRICTION_RANGE and MASS_RANGE come from, and how would you justify them to a plant engineer?
  • Using your --range wide run, explain why too wide a range can stop learning altogether.
  • How would you choose the ranges if you could measure five real cartons?

Realism and the render budget

What BlenderProc renders and labels, and what each step of realism costs.

  • Walk through synth/render_parts.py: where are the camera, lights and materials set, and where are the labels written?
  • Which details of the images matter for detecting parts, and which are wasted render time?
  • What does "photorealistic" (Outcome CO4) require for this task, and what can you afford on CPU?

Submit

  • A short written walkthrough of the one you chose, under Analyze in NOTES.md, quoting the lines you explain, with a screenshot of the run you describe in screenshots/.

4 · Understand & Refine

Week 6 · Wed–ThuNo AI assistant for this part

The mastery check — by hand, no AI assistance for this stage.

By hand this time. Turn off your AI assistant (Copilot: the status-bar icon, then Disable completions) and close its chat. Docs, the lecture and your own Week 5 code are fine.

Friction and mass aren't the only things reality varies. Randomize one more parameter by hand in simulation/randomize.py: one the extended held-out set changes and your policy never trained on.

  1. Pick the parameter: the arm's motor strength (model.actuator_gear), noise on the carton's observed position, or a one-step delay on actions. Write two sentences: why a real cell varies it, and the range you'll use and why.
  2. By hand, add it to randomize() (or to PushEnv, for noise or delay), with its range in simulation/config.py.
  3. Retrain the randomized policy with seed=0.
  4. Evaluate it with python evaluate.py --worlds heldout-plus next to your Week 5 randomized policy. Screenshot the table.
  5. Explain in 3–4 sentences what changed, what it cost, and one thing a real cell does that no randomization of yours covers.

Submit

  • Apply: The parameter you randomized by hand in simulation/randomize.py is committed, and evaluate.py --worlds heldout-plus works.
  • Understand: your own explanation under Understand & Refine in NOTES.md, with its screenshots in screenshots/.
  • Then push by the end of Week 6. Your repo is the submission; the last push before the deadline counts.

Common snags

  • run_once fails with an OpenGL or EGL error — headless rendering needs MUJOCO_GL=osmesa, which the .devcontainer sets. Run echo $MUJOCO_GL; if it's empty, open a new terminal or set it yourself.
  • Training is ten times slower than expected — the environment reloads the XML every episode. Change model.geom_friction and model.body_mass on the loaded model instead.
  • The randomized policy never learns — check the ranges in simulation/config.py: factors, not absolute values. A friction factor of 0.0 makes the carton unpushable.
  • BlenderProc stops with "no space left on device" — the Blender download and its cache need about 1.5 GB. Delete renders/ from earlier runs, and keep --n at 200.
  • export_usd can't import pxr — the usd-core package provides it; reinstall from requirements.txt. Don't install the full USD build from source.
  • The assistant created a new folder or project — it built in a new workspace instead of your starter. Delete what it made, reopen the repo folder, and say "this existing workspace" in Agent mode.

Most snags trace back to a concept. If one doesn't make sense, see Concept Companion → Module 3.
