How to use this page

Course rules this page follows: everything below runs in a GitHub Codespace on its free monthly hours, on CPU, and needs no credit card. Mosquitto, Node-RED, InfluxDB, Grafana, PyTorch, DeepXDE, MuJoCo, OpenUSD, BlenderProc and SimPy are free and need no account. Only HOS 4 uses an API key, on Gemini's free tier.

What "starter code" means in this course

Each HOS has a starter-code template repository on GitHub. You get your own copy by accepting that HOS's GitHub Classroom invite, linked from its lesson, and that copy is also your submission. Each HOS starts from its own small project, so you don't carry bugs from one HOS to the next. Your first job in each HOS is reading working code you didn't type. This page explains that code, one HOS at a time.

Planned, and subject to change. The starter repositories are being built and tested. This page describes the layout they're being built to; if a file name differs in your repo, your repo is right. Don't read ahead either: each section can give away the previous HOS's answers.

1️⃣

Starting HOS 1: Digital Shadows, Twins & Real-Time Pipelines

Planned layout
Sensors, a broker and an empty twin

A simulated floor of sensors, the Mosquitto–Node-RED–InfluxDB–Grafana stack in one compose file, and a twin that subscribes but doesn't check anything yet. The data-quality rules and the arrow back are yours.

requirements.txt + .devcontainer/ — setup, done for you in the Codespace

The .devcontainer/ folder tells GitHub how to build your Codespace: a Python container with Docker inside it, then pip install -r requirements.txt. You don't run any of it yourself. Everything is pinned to CPU builds, so nothing waits for a GPU you don't have.

docker-compose.yml — the data connection

Four services: Mosquitto (the broker, on port 1883), Node-RED (routing, 1880), InfluxDB (storage, 8086) and Grafana (the dashboard, 3000). docker compose up -d starts them; Codespaces offers each port in the Ports tab. The Node-RED flow and the Grafana dashboard are already provisioned, so a fresh stack shows data in about a minute.

Watch out: stopping a service (docker compose stop mosquitto) is how the HOS tests a dropout. Start it again before you move on.
sensors/simulate.py — the physical entity, simulated

Publishes a reading for each room on a floor, once a second, to topics like building/floor3/r2/temp. Each payload is JSON with ts (the sensor's own time), seq and value. python -m sensors.simulate runs it; flags inject the faults from data/faults/ (stuck, spike, dropout) at a chosen time.

data/normal_hour.csv + data/faults/ — recorded runs

One normal hour and one file per fault, so you can replay the same data and compare your rules on it. Replays use the recorded ts, so latency numbers from a replay mean nothing; measure latency on live data.

twin/floor.py — the virtual entity

Subscribes with paho-mqtt (version 2 API) and keeps each room's latest state: value, ts, seq. python -m twin.floor prints it. It believes every reading it gets, which is the problem you fix.

twin/quality.py — yours (Create)

Empty functions with docstrings for stuck, spike, dropout and stale checks. Your rules go here, and the twin calls them on every reading. tests/test_quality.py has one passing example to copy.

twin/control.py — yours (Refine): the arrow back

Off unless you start it as TWIN_MODE=1 python -m twin.control. It publishes a setpoint back to the floor, which turns your shadow into a twin. It must refuse to act on a reading your quality checks have flagged.

tools/latency.py — measures each hop

python -m tools.latency subscribes, compares arrival time with each payload's ts, and prints the median and worst delay. Run it while the dashboard is busy, too; the worst case is the number that matters.

tests/ — the checks that grade your rules

A few tests come with the starter and pass already; the HOS asks you to add your own. pytest from the top folder runs them all.

NOTES.md + screenshots/ — your evidence

The Engagement section of the HOS: what you ran, what you saw, and what you decided, with a screenshot for each claim. It's graded from your repo, so write it as you go, not on the last night.

Starting HOS 2: Physics-Informed Neural Networks

Planned layout
Wall data and a data-only baseline

Readings from three sensors in a wall during a cold snap, a finished data-only model to beat, and a PINN with its physics term still to write.

requirements.txt + .devcontainer/ — setup, done for you in the Codespace

The .devcontainer/ folder tells GitHub how to build your Codespace: a Python container with PyTorch for CPU and DeepXDE, then pip install -r requirements.txt. You don't run any of it yourself. Everything is pinned to CPU builds, so nothing waits for a GPU you don't have.

data/wall_coldsnap.csv — the readings

Twelve hours of temperature at three depths in a wall, with some noise, plus the inside and outside air temperatures that are the boundary conditions. Some hours are held back so you can test past the data.

models/data_only.py — the baseline

A small network fit to the readings alone. It looks good at the sensors; the HOS has you check it between them and past the data.

models/pinn_torch.py — yours (Create): the physics term

The network, the data term and the boundary terms are written. The physics term is a TODO: sample collocation points, take ∂u/∂t and ∂²u/∂x² with torch.autograd.grad, and add the weighted residual to the loss. Inputs are scaled to [0, 1], so α is scaled too: the docstring shows how.

Watch out: the second derivative needs create_graph=True on the first. Without it the physics term silently stays at zero.
models/pinn_deepxde.py — the same problem in a library

The same wall set up in DeepXDE, for comparison: fewer lines, less control. You'll compare its answer with yours in Evaluate.

compare.py — the scoreboard

python compare.py --model both trains both models (a few minutes on CPU) and prints error at the sensors, between them and past the data, and counts predictions that break the maximum principle. --check-physics prints the residual; --learn-alpha makes α a learnable parameter.

tests/ — the checks that grade your rules

A few tests come with the starter and pass already; the HOS asks you to add your own. pytest from the top folder runs them all.

NOTES.md + screenshots/ — your evidence

The Engagement section of the HOS: what you ran, what you saw, and what you decided, with a screenshot for each claim. It's graded from your repo, so write it as you go, not on the last night.

Starting HOS 3: Simulation, Synthetic Data & Sim-to-Real

Planned layout
A cell in MuJoCo, a scene and a renderer

A small pushing task in MuJoCo with a training script that already runs on CPU, its scene in OpenUSD, and a BlenderProc script for synthetic images. Where the randomization ranges come from, and the honest evaluation, are yours.

requirements.txt + .devcontainer/ — setup, done for you in the Codespace

The .devcontainer/ folder tells GitHub how to build your Codespace: a Python container with MuJoCo, Gymnasium, Stable-Baselines3, usd-core and BlenderProc, then pip install -r requirements.txt. You don't run any of it yourself. Everything is pinned to CPU builds, so nothing waits for a GPU you don't have.

simulation/cell.xml — the cell in MJCF

A table, a carton and a pusher arm, described in MuJoCo's XML. Friction, mass and motor strength are set here once; the randomizer overrides them each episode.

simulation/config.py + randomize.py — yours (Create): the ranges

config.py holds the ranges, all zero-width to start, so every episode is the same world. randomize.py applies them at each reset. Choosing the ranges, and writing down where each came from, is the Create stage.

train.py — PPO on CPU

python train.py trains a Stable-Baselines3 PPO policy for a set number of steps (around ten minutes on two cores) and saves it. Keep the step count the HOS gives you so runs are comparable.

evaluate.py — held-out worlds

python evaluate.py --worlds heldout runs the saved policy on worlds with altered physics inside the training ranges; --worlds heldout-plus adds some outside them. It prints the success rate per world, not just the average.

scene/cell.usda — the same cell in OpenUSD

A text USD file you can open in any editor: the same objects with their transforms and materials. It's what BlenderProc reads, and the format larger platforms share.

synth/render_parts.py + check_labels.py — synthetic images

blenderproc run synth/render_parts.py --n 200 renders labeled images into renders/ on CPU, with low samples and small images to fit the time. python synth/check_labels.py draws the boxes so you can check the labels before trusting them.

Watch out: rendering is the slowest step on CPU. Start with --n 20 to check the setup, then do the full run while you work on something else.
tests/ — the checks that grade your rules

A few tests come with the starter and pass already; the HOS asks you to add your own. pytest from the top folder runs them all.

NOTES.md + screenshots/ — your evidence

The Engagement section of the HOS: what you ran, what you saw, and what you decided, with a screenshot for each claim. It's graded from your repo, so write it as you go, not on the last night.

Starting HOS 4: What-If Testing & Safe Autonomous Decisions

Planned layout
A building model, a sweep and an agent with no limits

A SimPy model of one floor, a what-if sweep, and an ADK agent that can change setpoints with nothing to stop it. The envelope, and the log that proves it works, are yours.

requirements.txt + .devcontainer/ — setup, done for you in the Codespace

The .devcontainer/ folder tells GitHub how to build your Codespace: a Python container with Docker inside it, for the broker, then pip install -r requirements.txt. You don't run any of it yourself. Everything is pinned to CPU builds, so nothing waits for a GPU you don't have.

.env.example — where your API key goes 
# Your free Gemini API key — https://aistudio.google.com/apikey
GOOGLE_API_KEY=paste-your-key-here
GOOGLE_GENAI_USE_VERTEXAI=FALSE

Copy it to .env and put your real key there; .env is git-ignored. HOS 4 is the only HOS that needs a key: see the Account Setup Guide.

twin/floor_sim.py + config.py — the building, in SimPy

One floor's rooms, the cooling units and the people, as SimPy processes. python -m twin.floor_sim --outside 34 --capacity 1.0 --people 40 runs one afternoon in well under a second and prints the hottest room. config.py holds the defaults.

whatif/sweep.py — the what-if sweep

python -m whatif.sweep runs one factor at a time; --combined runs every combination, with several seeds each, and writes results/sweep_worst.csv. A few hundred runs take a couple of minutes on CPU.

agent/hvac_agent/agent.py — the agent

An ADK agent on gemini-3.8-flash with two tools: read the twin's state, and set a room's setpoint. Its instruction asks it to be careful, which is all that stands between it and the building at the start.

agent/envelope.py — yours (Create): the safety envelope

A before_tool_callback with a TODO. Return None to allow a call, or a dict to block it and hand the agent the reason. Every limit you add should point to a row in your sweep results. tests/test_envelope.py runs it without the model.

agent/scenarios.py + logs/actions.jsonl — scripted afternoons and the action log

python -m agent.scenarios plays scripted afternoons (normal, a failed unit, a stuck sensor) through the agent and appends every proposal, verdict and reason to logs/actions.jsonl, one JSON object per line.

tests/ — the checks that grade your rules

A few tests come with the starter and pass already; the HOS asks you to add your own. pytest from the top folder runs them all.

NOTES.md + screenshots/ — your evidence

The Engagement section of the HOS: what you ran, what you saw, and what you decided, with a screenshot for each claim. It's graded from your repo, so write it as you go, not on the last night.

Running it

In your Codespace: accept the HOS invite, open your repo, then Code → Codespaces → Create codespace on main. The devcontainer installs everything, which takes a few minutes the first time. Then, from the repo's top folder:

# HOS 1: start the stack, then the sensors and the twin (separate terminals)
docker compose up -d
python -m sensors.simulate
python -m twin.floor

# HOS 2: train and compare both models
python compare.py --model both

# HOS 3: train, test on held-out worlds, render a few images
python train.py
python evaluate.py --worlds heldout
blenderproc run synth/render_parts.py --n 20

# HOS 4: sweep, then run the agent's developer UI
python -m whatif.sweep --combined
adk web --allow_origins "*"

# Any HOS: run the tests
pytest

Ports (Grafana on 3000, Node-RED on 1880, the ADK UI on 8000) open from the Ports tab; plain adk web shows a blank page in a Codespace, which is why the command above has --allow_origins "*". The full setup, with a first run, is in Tools you'll use all term.

Stop your Codespace when you're done (Code → Codespaces → ⋯ → Stop codespace), because free hours are limited, and a running Docker stack uses them while you're away.

How to read code you didn't write

  1. Start at the entry point. That's sensors/simulate.py, compare.py, train.py or whatif/sweep.py, depending on the HOS.
  2. Follow one reading end to end. Pick one sensor value, one training point or one afternoon, and trace it file by file before you read anything else.
  3. Run it before you change it. Watch the normal case, then a fault. Real behavior beats guessing.
  4. Break it on purpose. Stop the broker, set a wrong α, widen a range to absurd values, ask the agent for 30 °C. Knowing how it fails is how you know you understand it.

This is the same habit the Evaluate and Analyze stages of every HOS are training.
