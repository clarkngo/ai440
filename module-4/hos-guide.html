HOS 4: What-If Testing & Safe Autonomous Decisions

Run what-if sweeps on a simulated floor during a heat wave, find the combined failure the single tests miss, let an ADK agent change setpoints over MQTT, then write the safety envelope it can't break, from your own sweep results.

Before you start

  1. Know the concepts. Read Concept Companion → Module 4 and try its self-check before you open the starter code.
  2. Rehearse it. The What-If & Safety Envelope Simulator plays the finished build in your browser; its guided tour takes about 15 minutes.

What you'll need

  • Starter code: your own HOS 4 repo, opened in GitHub Codespaces. Planned The HOS 4 starter repository and its GitHub Classroom invite are being built and tested; the invite link goes here when they are published. Not sure what a file does? See the starter code walkthrough for this HOS.
  • A GitHub account and a free Gemini API key from Google AI Studio (no credit card). It goes in .env as GOOGLE_API_KEY.
  • The default 2-core Codespace. The sweep (480 runs) takes a few minutes; only the Mosquitto container runs this time.

Reference reading (optional, before you start)

  • SimPy in 10 minutes: processes, events and timeouts, as twin/floor_sim.py uses them.
  • ADK: types of callbacks: what before_tool_callback receives, and what returning a dict does.
  • NIST AI Risk Management Framework: the vocabulary of risk, oversight and accountability your Analyze can borrow.

This HOS is graded across four stages instead of on code correctness alone: Engagement (Create/Scaffold) is 20% of the HOS grade, and Skills is 80%: Evaluate, Analyze, Apply (the change you make by hand in Understand & Refine) and Understand (your own explanation of it), 20% each. Each stage below says exactly what to submit. Everything goes in your Module 4 GitHub Classroom repo: written work under the matching heading in NOTES.md, screenshots in screenshots/. Commit and push as you go. By the end of Week 8, push your final work: your repo is your submission, so there is nothing to submit in Brightspace, and your last push before the deadline is what counts.

1 · Create / Scaffold

Week 7 · Wed–Thu

Graded as Engagement: 20% of this HOS. The AI-built starting point, not the deliverable.

Get a what-if sweep running on the floor model, with an AI coding assistant's help, and an ADK agent reading the twin and proposing setpoint changes over MQTT through a safety check that allows everything. The floor model, the agent's two tools and the logging are in the starter. This is the starting point, not the deliverable; whether it's safe is what Evaluate is for.

  1. Open your own HOS 4 repo in GitHub Codespaces. Copy .env.example to .env and paste your free Gemini API key. Planned The HOS 4 starter repository and its GitHub Classroom invite are being built and tested; the invite link goes here when they are published.
  2. Run one afternoon to see the model: python -m twin.floor_sim --outside 34 --capacity 1.0 --people 40 prints each room's temperature every 15 minutes.
  3. Give your assistant the prompt below, then run python -m whatif.sweep and open plots/sweep_heatmap.png.
  4. Start the broker and the agent: docker compose up -d mosquitto, then adk web --allow_origins "*", open the forwarded port, pick hvac_agent and ask it to keep Floor 3 comfortable through the afternoon.

The prompt

Use an AI coding assistant in Agent mode (GitHub Copilot is free for students in Codespaces). Give it this prompt as written, and read what it changed before you run anything:

In THIS existing workspace (the starter-code folder that's already open),
edit files here; do not create a new workspace or project.
In whatif/sweep.py, write a what-if sweep over the SimPy floor model
(run_afternoon() in twin/floor_sim.py):
- Factors: outside peak 30, 34, 38, 42 °C; HVAC capacity 1.0, 0.75,
  0.5, 0.0 (0.5 = one of two units failed at 14:00); occupancy
  20, 60, 100 people. 10 seeds per combination.
- For each run record each room's maximum temperature and the
  minutes above COMFORT_MAX (from twin/config.py).
- Write every run to results/sweep.csv and, per combination, the
  worst room's worst seed to results/sweep_worst.csv.
- Draw plots/sweep_heatmap.png: outside temperature x capacity, one
  panel per occupancy, colored by minutes above COMFORT_MAX.
- Add a --combined flag that also sticks r2's sensor at its 13:30
  reading (use stuck_sensor() from twin/faults.py).
It must finish in under 5 minutes on a 2-core Codespace (CPU only).
Make pytest pass. Do not change agent/envelope.py.

Gotchas to expect: (1) The assistant may build in a new workspace instead of your starter folder; use Agent mode and say "this existing workspace". (2) Plain adk web returns 403 errors in Codespaces; always use adk web --allow_origins "*". (3) The starter's .env.example names gemini-3.8-flash; older model names return errors for new free keys. (4) If the assistant "helpfully" adds limits to agent/envelope.py, undo them: writing the envelope from your own sweep is your Week 8 work.

Submit (Engagement)

  • Paste the prompt you gave your AI assistant under Create in NOTES.md, add plots/sweep_heatmap.png and a screenshot of the agent's first actions in adk web to screenshots/, then commit and push to your Module 4 repo.

2 · Evaluate

Week 7 · Fri–Sun

The critical gate — is the AI-built result actually right?

Does the sweep find the real failures, and what does the agent do when nothing stops it? python -m agent.scenarios replays five scripted afternoons through the agent with the permissive envelope: a heat wave, a failed unit, a stuck sensor, a request to set every room to 16 °C, and a noisy sensor. Run each of these and write down what happened:

  • Where it fails: from results/sweep_worst.csv, which combinations push a room past comfort, and which room? Check one cell by hand against twin.floor_sim.
  • Combined failure: run python -m whatif.sweep --combined. Which cells get worse with a stuck sensor added, and why does the floor model alone not show it?
  • Unsafe actions: run python -m agent.scenarios. List every action the agent took that you would block, and the scenario it came from.
  • The log: open logs/actions.jsonl. For one bad action, can you tell from the log alone which layer failed: the sensor, the model, the envelope or the agent? What's missing?

Submit

  • Paste this note under Evaluate in NOTES.md, add the heatmaps and the scenario output to screenshots/, then commit and push by the end of Week 7. Your commit history is your Week 7 checkpoint.

3 · Analyze

Week 8 · Mon–Tue

Why does this work, mechanically?

Pick one of these and explain it in your own words. Depth beats breadth: one mechanism explained well scores higher than a tour of every file. Your instructor may ask a follow-up about one line, so write it so you could answer.

The sweep

What it ran, what it skipped, and where the boundary is least certain.

  • Which combinations did your sweep run, and which plausible ones did it skip? Why those?
  • Where on the heatmap is the boundary between safe and unsafe least certain, and what would make it sharper?
  • Explain, from twin/floor_sim.py, why the combined failure is worse than either failure alone.

The callback and the envelope

How before_tool_callback stops a tool call before it reaches MQTT.

  • Trace one set_setpoint call from the agent through check_envelope to the MQTT publish. Quote the lines where it could be stopped.
  • What does returning a dict from the callback do, and what does the agent see?
  • Why does this check belong in a callback rather than in the agent's instruction?

The action log

Trace one bad outcome back to the layer that failed.

  • Take one unsafe action from your scenarios. Using only logs/actions.jsonl, which layer failed?
  • Who should fix that layer, and what would the fix be?
  • Name one field missing from the log that would have made the answer certain.

Submit

  • A short written walkthrough of the one you chose, under Analyze in NOTES.md, quoting the lines you explain, with a screenshot of the run you describe in screenshots/.

4 · Understand & Refine

Week 8 · Wed–ThuNo AI assistant for this part

The mastery check — by hand, no AI assistance for this stage.

By hand this time. Turn off your AI assistant (Copilot: the status-bar icon, then Disable completions) and close its chat. Docs, the lecture and your own Week 7 code are fine.

The permissive stub in agent/envelope.py allows everything. Write the real envelope by hand, from your own sweep results: every number in it should point to something you tested.

  1. Write two sentences: which sweep results your limits come from, and one situation your envelope can't protect against.
  2. By hand, write check(args, state) in agent/envelope.py with three rules: a state limit (the setpoint range your sweep showed safe), a rate limit (how often and how far a setpoint may change), and a stop-and-alert condition (for example, a sensor that hasn't changed in 20 minutes during a heat wave, or capacity below the level where your sweep failed). Return ("allow" | "block" | "stop_alert", reason).
  3. Run pytest tests/test_envelope.py, then rerun python -m agent.scenarios.
  4. Compare the agent's actions with your Week 7 run: what was blocked, what got through, and what stopped and alerted. Screenshot both runs.
  5. Explain in 3–4 sentences what your envelope costs on a normal afternoon (blocked actions that were fine) and what it still lets through.

Submit

  • Apply: The envelope you wrote by hand in agent/envelope.py is committed, tests/test_envelope.py passes and agent.scenarios runs.
  • Understand: your own explanation under Understand & Refine in NOTES.md, with its screenshots in screenshots/.
  • Then push by the end of Week 8. Your repo is the submission; the last push before the deadline counts.

Common snags

  • adk web opens a blank page with 403 Forbidden — in Codespaces, start it as adk web --allow_origins "*" and hard-refresh. That's safe there: Codespace ports are private to your GitHub account by default.
  • 502 Bad Gateway, a 404 or "model not found" — almost always the model name. Assistants default to older names, such as gemini-2.5-flash, that new keys can't use. Set it back to gemini-3.8-flash, as in .env.example.
  • 429 RESOURCE_EXHAUSTED — the free tier's per-minute limit. Wait a minute; agent.scenarios --pause 5 spaces out the five afternoons.
  • The callback never runs — it must be passed as before_tool_callback= on the Agent that owns the tools, and its signature is (tool, args, tool_context). A typo in the name raises no error; the agent just runs without it.
  • The sweep heatmap is all one color — the metric is wrong, not the model: check that COMFORT_MAX comes from twin/config.py and that minutes above it are summed per room, not per floor.
  • The assistant created a new folder or project — it built in a new workspace instead of your starter. Delete what it made, reopen the repo folder, and say "this existing workspace" in Agent mode.

Most snags trace back to a concept. If one doesn't make sense, see Concept Companion → Module 4.
