Why everything runs in a Codespace

Digital twins need a small stack of services: a message broker, a database, a dashboard, a physics engine. Installing those on every laptop goes wrong in a hundred ways. Each AIC repo describes its whole environment in a .devcontainer, so GitHub builds the same Linux machine for everyone, in the browser, with nothing to install. It has two CPU cores and no GPU, and every build in this course is sized to fit.

GitHub Codespaces

Every AIC

A Codespace is a Linux machine in the cloud with VS Code in your browser. You open one from a repo, and it's ready when its .devcontainer finishes installing.

  1. Open your AIC repo on github.com, click Code → Codespaces → Create codespace on main.
  2. Wait for the first build (a few minutes; later starts take seconds). The terminal at the bottom shows progress.
  3. Keep the default 2-core machine. It's enough for every AIC, and bigger machines use your free hours faster.
  4. When you finish, stop it: Code → Codespaces → ⋯ → Stop codespace, or let it stop itself after 30 idle minutes.
Free hours. Personal GitHub accounts include a monthly allowance of Codespaces core-hours (120 core-hours, which is 60 hours on a 2-core machine), and GitHub Pro, free with the Student Developer Pack, includes more. Stop Codespaces you aren't using, and delete old ones from github.com/codespaces, since stored Codespaces count against a storage allowance too.
Rebuilds. If a repo's .devcontainer changes after you created the Codespace, open the Command Palette (Cmd/Ctrl+Shift+P) → Codespaces: Rebuild Container. Your files are kept.

First run: one AIC repo, start to finish

Every AIC starts with these same steps. The repo comes from the AIC invite link in each module. Planned The AIC 1 starter repository and its GitHub Classroom invite are being built and tested; the invite link goes here when they are published.

  1. Open the repo in a Codespace, as above. The .devcontainer installs Python, the project's packages and Docker.
  2. Read the README, then NOTES.md: its four headings (Create, Evaluate, Analyze, Understand & Refine) are where your written work goes.
  3. Add keys only if the AIC needs them (AIC 4 does): copy .env.example to .env and fill it in.
  4. Run the tests to see the starting point: python -m pytest. Most fail until you build the missing parts. That's the to-do list.
  5. Commit and push after each stage: 
    git add -A
git commit -m "AIC 1: Create"
git push
  6. Your repo is your submission. There's no Brightspace upload for an AIC; the last push before the end of the AIC's second week is what's graded.

Docker, services and forwarded ports

AIC 1 and AIC 4

AIC 1 runs four services in containers (Mosquitto, Node-RED, InfluxDB and Grafana), and AIC 4 runs Mosquitto again. Docker Compose starts them all from one file.

docker compose up -d          # start everything in docker-compose.yml, in the background
docker compose ps             # what's running, and on which port
docker compose logs -f grafana   # follow one service's log (Ctrl+C to stop following)
docker compose stop mosquitto    # stop one service (AIC 1 Evaluate does this on purpose)
docker compose down           # stop and remove them all

Inside the Codespace vs. in your browser

Your Python code talks to the services by name and port inside the Codespace, such as localhost:1883 for the MQTT broker. Your browser can't reach localhost there; it uses the forwarded URLs in the Ports tab (Grafana on 3000, Node-RED on 1880, adk web on 8000).

Why it matters: forwarded ports are private to your GitHub account by default. Leave them that way: nobody else needs your dashboard.

Memory is the limit

The full AIC 1 stack uses about 1.5 GB. If a container keeps restarting, run docker compose ps and stop what you don't need, or close other Codespaces.

Local passwords

InfluxDB and Grafana need an admin password. The starter's .env.example sets local-only defaults for them. They protect nothing outside your Codespace, so don't reuse a real password there.

Universal tooling

Read before Week 1

These show up in every AIC, not just one.

The terminal

Where you run the simulator, the tests and the training scripts. A new terminal tab starts at the repo's top folder; many AIC steps need two or three tabs at once (the sensors in one, the twin in another).

Packages and the devcontainer

Each repo pins its packages in requirements.txt, and the devcontainer installs them. Some are large (PyTorch, MuJoCo), so the starters pin CPU-only builds.

Why it matters: if an AI assistant "helpfully" installs a GPU build of PyTorch, the Codespace runs out of disk. Don't let it change requirements.txt.

.env files and API keys

A key is a password for a service. It lives in .env, which each repo's .gitignore keeps out of Git. Never paste it into code, a chat or a screenshot.

Git

Commit after each stage with a message that says which stage. Your commit history is your Week 1 checkpoint for each AIC, and in the Term Project it shows who built what.

Working with an AI coding assistant

GitHub Copilot is built into Codespaces (free for verified students). The Create stage of each AIC is deliberately AI-driven; use Agent mode, and tell it to work in "this existing workspace". The rest of each AIC proves, in writing and by hand, that you understand what it built.

Why it matters: getting the AI-built version running is 12 of each AIC's 100 points (Build: Create). The other 88 are for judging it, explaining it and extending it without AI help.

Quick self-check before you continue

  • Could you open a repo in a Codespace, run its tests and push a commit?
  • Do you know why your code uses localhost:1883 but your browser uses the Ports tab?
  • Do you know which part of each AIC is done with an AI assistant, and which you must do yourself?
