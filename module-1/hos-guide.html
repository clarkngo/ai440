HOS 1: Digital Shadows, Twins & Real-Time Pipelines

Stream a floor of simulated building sensors over MQTT into a virtual entity that keeps each room's live state, measure the delay hop by hop, break the pipeline on purpose, then teach the twin when not to believe its sensors.

Before you start

  1. Know the concepts. Read Concept Companion → Module 1 and try its self-check before you open the starter code.
  2. Rehearse it. The Sensor Pipeline Simulator plays the finished build in your browser; its guided tour takes about 15 minutes.

What you'll need

  • Starter code: your own HOS 1 repo, opened in GitHub Codespaces. Planned The HOS 1 starter repository and its GitHub Classroom invite are being built and tested; the invite link goes here when they are published. Not sure what a file does? See the starter code walkthrough for this HOS.
  • A GitHub account. Nothing else: the broker, database and dashboard run in Docker inside your Codespace.
  • A Codespace with at least 2 cores (the default). The stack (Mosquitto, Node-RED, InfluxDB, Grafana) uses about 1.5 GB of memory; close other Codespaces if it won't start.

Reference reading (optional, before you start)

  • MQTT: getting started: topics, publish/subscribe and QoS in ten minutes.
  • paho-mqtt 2.0 migration notes: why 1.x examples break, and the CallbackAPIVersion.VERSION2 callbacks.
  • InfluxDB 2 get started: buckets, measurements and Flux queries, as the Grafana panels use them.

This HOS is graded across four stages instead of on code correctness alone: Engagement (Create/Scaffold) is 20% of the HOS grade, and Skills is 80%: Evaluate, Analyze, Apply (the change you make by hand in Understand & Refine) and Understand (your own explanation of it), 20% each. Each stage below says exactly what to submit. Everything goes in your Module 1 GitHub Classroom repo: written work under the matching heading in NOTES.md, screenshots in screenshots/. Commit and push as you go. By the end of Week 2, push your final work: your repo is your submission, so there is nothing to submit in Brightspace, and your last push before the deadline is what counts.

1 · Create / Scaffold

Week 1 · Wed–Thu

Graded as Engagement: 20% of this HOS. The AI-built starting point, not the deliverable.

Get the virtual entity and a latency probe running with an AI coding assistant. The sensors, broker, database and dashboard already run in the starter; your assistant builds the part that keeps each room's live state. This is the starting point, not the deliverable. It's also the only HOS where the full prompt is given to you.

  1. Open your own HOS 1 repo in GitHub Codespaces (its .devcontainer installs Python and Docker). Planned The HOS 1 starter repository and its GitHub Classroom invite are being built and tested; the invite link goes here when they are published.
  2. Start the stack and the sensors: docker compose up -d, then python -m sensors.simulate in its own terminal. Open Grafana from the Ports tab (port 3000) and check that the Floor 3 dashboard is moving.
  3. Give your assistant the prompt below, then run python -m twin.floor in a second terminal and python -m tools.latency in a third.

The prompt

Use an AI coding assistant in Agent mode (GitHub Copilot is free for students in Codespaces). Give it this prompt as written, and read what it changed before you run anything:

In THIS existing workspace (the starter-code folder that's already open),
edit files here; do not create a new workspace or project.
The Docker stack (Mosquitto, Node-RED, InfluxDB, Grafana) and
sensors/simulate.py already run. Don't change docker-compose.yml
or pipeline/flows.json.
1. In twin/floor.py, write a FloorTwin class with paho-mqtt 2.x
   (CallbackAPIVersion.VERSION2) that subscribes to
   building/floor3/+/+ and keeps, for each room, the latest temp,
   co2 and occupancy, each with its sensor timestamp (ts), its
   sequence number (seq) and the time it arrived.
   - state(room) returns those readings plus age_s, the seconds
     since each one arrived.
   - Once a second, publish each room's state as JSON to
     twin/floor3/<room>/state.
   - Never publish to building/floor3/+/hvac/set. Control belongs
     to twin/control.py, and it stays off for now.
2. In tools/latency.py, subscribe to the sensor topics and to
   twin/floor3/+/state for 60 seconds, then print a table per room:
   median and worst delay from the sensor timestamp to (a) the
   broker and (b) the twin state, and how many seq numbers were
   missing.
3. Read the broker host, port and topics from twin/config.py.
4. Make python -m pytest tests/test_floor.py pass.

Gotchas to expect: (1) The assistant may build in a new workspace instead of your starter folder; use Agent mode and say "this existing workspace" (the prompt does). (2) Assistants often write paho-mqtt 1.x code. The starter uses 2.x, where the client needs CallbackAPIVersion.VERSION2 and the callbacks take an extra argument; if on_connect never fires, check this first. (3) Inside the Codespace the broker is localhost:1883; only your browser needs the forwarded port URLs.

Submit (Engagement)

  • Paste the prompt you gave your AI assistant under Create in NOTES.md, add a screenshot of the Floor 3 Grafana dashboard and of tools.latency's table to screenshots/, then commit and push to your Module 1 repo.

2 · Evaluate

Week 1 · Fri–Sun

The critical gate — is the AI-built result actually right?

Is the AI-built virtual entity actually right, and can it be trusted? Check the numbers it reports against the simulator's ground truth, and break the pipeline on purpose. Run each of these and write down what happened:

  • Latency, hop by hop: run tools.latency. What are the median and worst delays to the broker and to the twin state? Is that real-time enough for a room's heating, and how would you decide?
  • Stuck sensor: restart the simulator with --fault stuck --room r2. Does the twin state, Grafana or anything else notice? How long before you would?
  • Broker outage: docker compose stop mosquitto, wait 30 seconds, start it again. Which seq numbers were lost, how does Grafana draw the gap, and what does the twin's age_s say?
  • Turn the arrow on: with the stuck sensor still running, start TWIN_MODE=1 python -m twin.control. Compare room 2's true temperature (sim/truth/r2/temp) with what the twin believes. What did control do?

Submit

  • Paste this note under Evaluate in NOTES.md, add your screenshots to screenshots/, then commit and push by the end of Week 1. Your commit history is your Week 1 checkpoint.

3 · Analyze

Week 2 · Mon–Tue

Why does this work, mechanically?

Pick one of these and explain it in your own words. Depth beats breadth: one mechanism explained well scores higher than a tour of every file. Your instructor may ask a follow-up about one line, so write it so you could answer.

Shadow or twin: the one arrow

Draw the three components and every arrow between them, from your code.

  • Draw Floor 3's three components and every arrow between them. Which file or container is each one?
  • Quote the line in twin/control.py that makes this a twin. What has to be true before it runs?
  • What new failure became possible in Evaluate test 4 that wasn't possible in shadow mode?

Where the latency goes

Each hop, measured, and the slowest one explained.

  • Break the end-to-end delay into hops, using your tools.latency numbers. Which hop is slowest, and why?
  • Why can the twin state be fresher than the Grafana panel, even though both come from the same broker?
  • What happens to the twin if messages arrive out of order, and how would seq show it?

What the data can't tell you

Which faults look exactly like real readings, and why.

  • Which of the four faults looked exactly like a real reading in your runs, and which didn't?
  • Where in the pipeline should validation live, and why not only in Grafana?
  • What should the virtual entity report for a room whose newest reading is 90 seconds old?

4 · Understand & Refine

Week 2 · Wed–ThuNo AI assistant for this part

The mastery check — by hand, no AI assistance for this stage.

By hand this time. Turn off your AI assistant (Copilot: the status-bar icon, then Disable completions) and close its chat. Docs, the lecture and your own Week 1 code are fine.

The virtual entity believes every reading. Teach it when not to: write the data-quality check yourself, in twin/quality.py, and wire it in so a room that fails the check is marked unknown and control leaves it alone.

  1. Write each rule in one sentence, with the number you chose and why: how long may a reading stay unchanged, how fast can room air really change temperature, and how old may the newest reading be?
  2. Implement check(history) -> "ok" | "stuck" | "jump" | "stale" by hand in twin/quality.py.
  3. Wire it into FloorTwin: a room that fails is marked unknown, and twin/control.py skips unknown rooms.
  4. Write tests/test_quality.py: every recorded fault in data/faults/ is flagged, and data/normal_hour.csv raises no alarm. Screenshot the passing pytest run.
  5. Write 2–3 sentences: which fault your check still can't see (try a sensor that slowly drifts), and what it would take to catch it.

Submit

  • Apply: The twin/quality.py and tests/test_quality.py you wrote by hand are committed, and the tests pass.
  • Understand: your own explanation under Understand & Refine in NOTES.md, with its screenshots in screenshots/.
  • Then push by the end of Week 2. Your repo is the submission; the last push before the deadline counts.

Common snags

  • docker compose up hangs or a container keeps restarting — usually memory. Run docker compose ps; if InfluxDB or Grafana restarts, stop other Codespaces or rebuild this one with 4 cores (still free within the monthly quota).
  • on_connect never fires — paho-mqtt 1.x code on the 2.x library. Create the client with mqtt.Client(mqtt.CallbackAPIVersion.VERSION2); 2.x callbacks take an extra properties (and reason_code) argument.
  • Connection refused on port 1883 — inside the Codespace the broker is localhost:1883. Only your browser uses the forwarded URLs from the Ports tab, for Grafana (3000) and Node-RED (1880).
  • Grafana shows "No data" — check the time range (last 15 minutes), that sensors.simulate is still running, and that the Node-RED flow shows "connected" under its MQTT node.
  • The latency table shows negative delays — a clock mismatch: compare timestamps from the same clock. In the starter, all timestamps are the Codespace's clock in UTC seconds; check the assistant didn't mix in local time or milliseconds.
  • The assistant created a new folder or project — it built in a new workspace instead of your starter. Delete what it made, reopen the repo folder, and say "this existing workspace" in Agent mode.

Most snags trace back to a concept. If one doesn't make sense, see Concept Companion → Module 1.
